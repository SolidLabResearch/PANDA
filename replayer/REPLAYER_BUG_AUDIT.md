# Replayer Bug Audit

Scope: claims from `REPLAYER_ANALYSIS_FOR_PANDA.md` rechecked against source files.

Classification legend:
- Confirmed by source: the code directly shows the issue.
- Strong suspicion: the code strongly suggests the issue, but runtime behavior or external behavior still needs confirmation.
- Needs runtime check: source is insufficient to determine whether the issue manifests.
- Probably incorrect claim: the report’s claim does not match the code.

| Claim | File/function | Evidence | Confidence | Runtime impact | Fix difficulty | Recommended next action |
|---|---|---|---|---|---|---|
| Replay uses two fixed-rate `setInterval` loops instead of event-time deltas | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `replay_observations()` | `setInterval(() => this.process_queue(), 1000 / this.frequency)` and `setInterval(() => this.publish_one_observation(), 1000 / this.frequency_buffer)` are the only replay schedulers; no dataset delta logic exists | Confirmed by source | Replay cadence is wall-clock driven, not event-time faithful | Low | Treat as design limitation; if faithful replay is required, replace timers with delta-based scheduling |
| Each replayed observation timestamp is rewritten to the current wall clock | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `publish_one_observation()` | `const time_now = new Date().toISOString();` then `addQuad(... hasTimestamp, literal(time_now))` | Confirmed by source | Downstream consumers cannot recover original event-time semantics | Low | Preserve original timestamp in a separate predicate or avoid rewriting at replay time |
| Authorization is pre-resolved at startup and cached per container | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `initialize()`, [`src/fetcher/ReuseTokenUMAFetcher.ts`](./src/fetcher/ReuseTokenUMAFetcher.ts), [`src/service/TokenManagerService.ts`](./src/service/TokenManagerService.ts) | `authorizeFetch()` calls `preAuthorize()` for every container; `TokenManagerService` stores tokens in a `Map`; `fetch()` first checks cached token | Confirmed by source | Startup warmup and first-request auth cost are included unless isolated | Low | Time auth warmup separately and preload or stub it in benchmarks |
| Queue is drained only in batches sized to the number of target containers | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `process_queue()` | `const items_to_publish = this.queue.splice(0, this.containers_to_publish.length);` | Confirmed by source | Producer can outrun consumer and build backlog when enqueue rate exceeds network throughput | Low | Add queue-depth telemetry and consider backpressure or adaptive draining |
| Sort comparator likely compares RDF term arrays/objects rather than numeric timestamps | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `merge()` | `store.getObjects(...)` is compared with `if (timestamp_one > timestamp_two)`; the result is not converted to a scalar timestamp | Strong suspicion | Observation order may be unstable or incorrect, especially across RDF term shapes | Medium | Add a runtime sort sanity check on a small known dataset and log comparator inputs/outputs |
| Authorization header in replay POST path is malformed because it interpolates an object | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `publish_one_observation()` | `Authorization: \`Bearer ${this.token_manager_service.getAccessToken(container)}\`` where `getAccessToken()` returns an object | Confirmed by source | Requests can carry `Bearer [object Object]` instead of a token string, causing auth failures | Low | Split out `access_token` and `token_type` fields before constructing the header |
| Token manager getter/setter type mismatch is used incorrectly at the call site | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `publish_one_observation()`, [`src/service/TokenManagerService.ts`](./src/service/TokenManagerService.ts) / `getAccessToken()` | Getter returns `{ access_token, token_type }`; call site expects a string | Confirmed by source | Same as above: token header construction is wrong and may cause every POST to fail auth | Low | Fix the caller and add a unit test for header construction |
| `process_queue()` can overlap with itself because the timer does not await or lock the async drain | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `replay_observations()`, `process_queue()` | `setInterval(() => { this.process_queue(); }, ...)` ignores the returned promise, and there is no reentrancy guard | Confirmed by source | Concurrent drains can double-process queue items or reorder retries under load | Medium | Add an `isProcessingQueue` flag or single-flight lock and measure queue drain duration |
| Only one interval handle is stored and neither interval is cleared explicitly | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `replay_observations()` | `intervalId` exists for only one timer; the producer interval is anonymous; no `clearInterval()` path exists | Confirmed by source | Process cleanup is unmanaged; termination relies on `process.exit()` | Low | Store both timer handles and clear them in a shutdown path |
| Inbox extraction swallows errors and returns `undefined` on failure | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `extract_container_to_publish()`, [`src/Util.ts`](./src/Util.ts) / `extract_ldp_inbox()` | Both functions `catch (error) { console.error(error); }` without rethrowing | Confirmed by source | Callers may fail later with less context and misleading stack traces | Low | Re-throw with contextual metadata after logging |
| `update_latest_inbox()` uses `axios.patch` with a request body shaped like a fetch init object | [`src/Util.ts`](./src/Util.ts) / `update_latest_inbox()` | `axios.patch(ldes_location, { method: 'PATCH', headers: ..., body: ... })` passes method/body in the data position, not as Axios config | Strong suspicion | PATCH payload may not be sent as intended; inbox update can silently fail against stricter servers | Medium | Rewrite to proper Axios `patch(url, data, config)` usage and verify with a request capture |
| Replay start logging is misleading because it executes after `replay_observations()` resolves | [`src/index.ts`](./src/index.ts) / `main().then(...)` | `main()` awaits `replay_observations()`, but that method only sets timers and returns; the `"Starting the replay..."` log is emitted afterward | Confirmed by source | Operational logs do not reflect the actual replay start time | Low | Move the log into `replay_observations()` after both timers are armed |
| `UserManagedAccessFetcher` contains unreachable error handling code | [`src/fetcher/UserManagedAccessFetcher.ts`](./src/fetcher/UserManagedAccessFetcher.ts) / `fetch()` | `return asRequestResponse` precedes `throw Error(...)`, making the throw unreachable | Confirmed by source | Intended failure handling is masked; debugging auth failures is harder | Low | Remove dead code and make error propagation explicit |
| Full RDF dataset is ingested into memory before replay starts | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `load_dataset()` | `N3.StreamParser` pipes into `this.store` and resolves only after the parse ends | Confirmed by source | Startup time and memory use scale with dataset size | Low | Measure parse time and memory footprint; consider streaming or chunked ingestion if needed |
| Sort path is expensive because it repeatedly slices arrays and looks up timestamps during merge | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `sort_observations()`, `merge_sort()`, `merge()` | Recursive slice-based merge sort plus repeated `store.getObjects(...)` calls inside `merge()` | Confirmed by source | Startup sort time can dominate large datasets | Medium | Add sort timing and consider precomputing timestamp keys |
| Startup authorization warmup is a benchmark-distorting cost | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `authorizeFetch()`, [`src/fetcher/ReuseTokenUMAFetcher.ts`](./src/fetcher/ReuseTokenUMAFetcher.ts) / `preAuthorize()` | `authorizeFetch()` runs `preAuthorize()` for every container before replay begins | Confirmed by source | First-run latency includes auth challenge, token exchange, and final authorized POST | Low | Instrument warmup separately and exclude it from steady-state replay numbers |
| `appendFileSync` adds disk I/O to the POST hot path | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `post_with_retry()` | Successful POSTs synchronously append to `replayer-log.csv` | Confirmed by source | Per-post latency includes blocking file I/O | Low | Move logging off the critical path or batch it |
| UMA fallback adds multiple network round trips on cache miss or rejected token | [`src/fetcher/ReuseTokenUMAFetcher.ts`](./src/fetcher/ReuseTokenUMAFetcher.ts) / `fetch()` | Cache-first logic falls back to tokenless request, challenge parse, token POST, and retry on 401 | Confirmed by source | First request per container and token-invalidations incur extra latency | Medium | Measure cache hit/miss rate and auth retry count; consider token expiry awareness |
| Post retries use exponential backoff and can dominate tail latency | [`src/publishing/PublishObservations.ts`](./src/publishing/PublishObservations.ts) / `post_with_retry()` | `delay = backoff * Math.pow(2, attempt - 1)` with up to 3 attempts | Confirmed by source | Failed or flaky endpoints inflate end-to-end replay time | Low | Record retry counts and per-attempt latency; decide whether retries belong in benchmark mode |
| `TokenManagerService` is in-memory only and has no expiry handling | [`src/service/TokenManagerService.ts`](./src/service/TokenManagerService.ts) | Tokens are stored in a process-local `Map` with no TTL or refresh logic | Confirmed by source | Cached tokens can go stale within a run; state is lost across runs | Medium | Add expiry metadata or force refresh on 401 |
| `create_ldp_container()` is probably not exercised in the replay path | [`src/Util.ts`](./src/Util.ts) / `create_ldp_container()` | The function exists, but `PublishObservations` does not call it | Probably incorrect claim as a hazard in this path | No direct runtime impact in current replay flow | Low | Leave it out of the replay audit unless future code paths call it |

## Notes

- The audit intentionally separates source-level certainty from runtime confirmation.
- Claims that are design limitations rather than bugs are still listed if they affect benchmark validity or replay semantics.
